# Support tickets (P7-T5)

Riders and drivers report problems (lost item, rude driver, wrong fare, safety) as **support tickets**. They are not bank chargebacks (P6-T7).
Code: `App\Services\Support\SupportTicketService` (every change), `App\Models\SupportTicket` / `SupportTicketMessage`.

## Data

`support_tickets`: `code` (`TKT-00042`, generated by the database from the id), `requester_id` (users), `requester_type` (`rider`|`driver`: the app the
ticket came from; one person can ride and drive), `trip_id` (optional, must be the requester's own trip), `subject`, `category`, `priority`, `status`,
`assigned_to`, `resolved_at`, `resolution`, `last_message_at`, `idempotency_key`.
`support_ticket_messages`: `ticket_id`, `author_id`, `body`, `is_internal_note`, `attachments` (jsonb, no upload endpoint yet), `created_at`. Append-only.

| Category | `fare`, `lost_item`, `safety`, `driver_behavior`, `rider_behavior`, `app_issue`, `other` |
| --- | --- |
| Priority | `low`, `normal`, `high`, `urgent`. A new ticket is `normal`, except **safety: `urgent`** |
| Status | `open` → `in_progress` / `waiting_on_customer` → `resolved` → (`closed`). `closed` is final; nothing writes it yet |

## Status rules

| Action | Allowed from | Result |
| --- | --- | --- |
| Requester opens | — | `open` |
| Staff reply (public) | open, in_progress, waiting_on_customer | `waiting_on_customer`; the replier claims an unassigned ticket; the requester gets a push |
| Internal note | same | no status change, no event, never returned by the mobile API |
| Assign / unassign | open, in_progress, waiting_on_customer | an `open` ticket becomes `in_progress` when assigned; only to an active admin with `support.manage` |
| Resolve (resolution **required**) | open, in_progress, waiting_on_customer | `resolved`, `resolved_at`, `resolution` |
| Reopen | resolved, closed | `open`, resolution cleared |
| Requester writes | open, in_progress, waiting_on_customer, resolved | waiting → `in_progress`; resolved → `open` (reopened, resolution cleared); `closed` is refused |

A refused action is `409` (a flash message in the admin). Every step runs in one transaction with the ticket row locked, so two staff members or a double click apply it once.

## Safety alert

A `safety` ticket is created `urgent` and, **after the commit**, every active admin with `support.manage` (support, admin, super admin by default) gets the
`SafetyAlert` mail (queued): ticket code, the linked trip code, and a link to `/admin/support-tickets/{id}`. The text the requester wrote is never in the
mail. The in-app bell is added by P13-T6.

## Mobile API (`/api/v1`, Sanctum, rider or driver app, `throttle:support-tickets`)

A blocked (suspended) account may still use these routes, so it can ask support why.

| Endpoint | |
| --- | --- |
| `POST /api/v1/support-tickets` | `{category, subject (3–160), message (1–5000), trip_id?}` → `201 {data: ticket}`. The app comes from the token, never the body |
| `GET /api/v1/support-tickets` | the caller's own tickets for the app they are using, newest activity first, 20 per page: `{data: [ticket], meta}` |
| `GET /api/v1/support-tickets/{id}` | one ticket with `messages: [{id, from: you\|support, body, created_at}]`. **Internal notes and staff names are never returned** |
| `POST /api/v1/support-tickets/{id}/messages` | `{body (1–5000)}` → `201 {data: {id, from, body, created_at, ticket_status}}` |

Ticket: `id, code, subject, category, priority, status, trip_id, resolution, resolved_at, last_message_at, created_at`.
Another person's ticket, or the same person's ticket from the other app, is `404`. A `trip_id` that is not the caller's own is `422` (it does not say whether it exists).

**Idempotency.** Both POSTs take an optional `Idempotency-Key` header (8–64 of `A-Za-z0-9_-`). The same key from the same person never creates a second
ticket or message: the retry answers `200` with the existing one; the same key with a different request is `409`.

## Admin (`support.manage` on every route)

`GET /admin/support-tickets` (filters `filter[status]`, `[category]`, `[priority]`, `[assignee]` = `me`, `unassigned` or an admin id, `[search]` = code, subject or
requester name; `?ticket=` selects one), `GET /admin/support-tickets/{id}` (the same page with that ticket open: the link in the alert),
`POST .../assign` (`assignee_id`, or `null`), `POST .../messages` (`body`, `internal`), `POST .../resolve` (`resolution`), `POST .../reopen`.
From a ticket with a linked trip the admin can open the trip; **Issue refund** (`payments.refund`, P6-T7) and **Adjust fare** (`trips.adjust_fare`, P7-T2)
are shown for those permissions and stay disabled until those tasks add their endpoints.

Each write is audited (`support_ticket.*`, see [audit-log.md](audit-log.md)) and publishes `support_ticket.updated` (reply, status, assignment) after the commit
(see [realtime-events.md](realtime-events.md)); internal notes publish nothing. The navigation badge counts urgent tickets that are open, in progress or waiting.
